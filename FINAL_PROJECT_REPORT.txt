ABSTRACT
========

This academic project presents a complete machine-learning-based framework for
detecting and classifying cyber threats in network traffic. Using the UNSW-NB15
intrusion detection dataset (257,673 flows), we built a supervised learning
pipeline with XGBoost as the primary classifier, achieving 91.13% binary accuracy
and 96.85% recall (crucial for detecting actual attacks). The system classifies
threats into 10 attack categories (DoS, Exploits, Backdoor, etc.), computes
experimental risk scores, and includes an Isolation Forest anomaly detector to
identify unusual flow patterns. All components are integrated into a Streamlit
dashboard and saved for reproducible deployment.

---

1. INTRODUCTION
===============

Network intrusion detection is a critical defensive security capability. Modern
attacks are frequent, sophisticated, and low-signature (polymorphic). Traditional
rule-based IDS systems (Snort, Suricata) struggle with unknown attack variants.

Machine Learning offers an alternative: learn attack patterns from historical data
and generalize to new threats. This project demonstrates the complete ML pipeline
for threat detection—from raw dataset to trained model to interactive dashboard.

---

2. PROBLEM STATEMENT
====================

Challenge:
  Given network flow statistics (packet counts, byte volumes, protocol info,
  connection state, flags), predict whether the flow is benign or malicious.
  If malicious, classify the attack type.

Real-world constraints:
  • Highly imbalanced data (attackers are the minority)
  • Diverse attack signatures (generic exploits vs. specific backdoors)
  • False positives are costly (alert fatigue)
  • False negatives are catastrophic (missed attacks)

Cybersecurity-specific metrics:
  • Recall (True Positive Rate): catch real attacks
  • FPR (False Positive Rate): avoid alert overload
  • Macro F1: balanced performance across minority attack types

8. DATA PREPROCESSING
=====================

Challenges Addressed:

  1. Categorical Features (proto, service, state)
     • proto had 133 unique values → bucketed to top 10 + 'other'
     • Prevents sparse one-hot encoding explosion
     • Keeps 99%+ of data

  2. Missing / Infinite Values
     • None detected; dataset is clean

  3. Duplicates
     • 67K exact duplicates within training set (flows with identical features)
     • Decision: KEPT (network data naturally has repeated signatures)
     • This is NOT a hidden data quality issue; it's documented

  4. Class Imbalance
     • Benign : Malicious = 1 : 2.13
     • Strategy: class_weight='balanced' in model training
     • Rationale: Moderate imbalance; synthetic oversampling (SMOTE) rejected
       because network flows are highly structured (synthetic copies risk creating
       unrealistic patterns)

  5. Scaling & Encoding
     • StandardScaler on numeric features (zero mean, unit variance)
     • OneHotEncoder on categorical features (drop first to avoid multicollinearity)
     • ColumnTransformer pipeline ensures no data leakage (fit only on train data)

13. MODEL COMPARISON & DISCUSSION
===================================

Why XGBoost won:

  1. Recall (0.9685)
     • Catches 96.85% of real attacks — critical for security
     • Random Forest (97.78%) is higher, but FPR is also higher (19.14% vs 15.87%)

  2. Precision-Recall Balance (F1: 0.9233)
     • Maintains good precision (8820) to avoid excessive false alarms
     • Unlike Decision Tree, avoids overfitting on training data

  3. False Positive Rate (0.1587, ~5,873 false alarms on 37K benign flows)
     • Reasonable for operational deployment
     • Security team can handle ~15% false alarm rate if recall is high

  4. Computational Efficiency
     • Gradient boosting inference is ~10x faster than Random Forest
     • Important for real-time packet classification

  5. Robustness
     • XGBoost internally handles class imbalance through sample weighting
     • Less prone to overfitting than Decision Tree

Trade-off accepted:
  Random Forest has slightly higher recall (97.78% vs 96.85%), but higher FPR
  means ~1.3K more false alarms. For this dataset, XGBoost's balance is optimal.

15. LIMITATIONS
================

Dataset-Level:
  1. Pre-extracted features (no raw traffic)
     • Real system would need live packet capture / flow collection
     • Feature engineering done offline; encoding is fixed

  2. Synthetic nature of UNSW-NB15
     • Generated in lab (2015) using Ixia traffic generator
     • Real-world traffic characteristics may differ
     • Adversaries aware of IDS signatures use evasion techniques

  3. Train/test temporal separation unknown
     • Dataset does not specify temporal order
     • Possible that train & test contain overlapping time periods
     • Real deployment requires time-based splitting to avoid leakage

  4. Imbalanced multiclass
     • Rare attack types (Worms: 44 samples) cannot be learned reliably
     • Binary classification is more reliable than multiclass

Model-Level:
  1. Feature importance is model-specific
     • XGBoost importances differ from Random Forest
     • No ground truth about which features actually drive attacks

  2. Risk score is experimental
     • Severity mapping (severity_map) is arbitrary, not validated
     • 0-100 scale is for demonstration only, not an official standard

  3. Anomaly detection (Isolation Forest)
     • Detects statistical outliers, NOT zero-day attacks
     • Many benign flows are anomalous (rare but legitimate traffic)
     • High false positive rate if deployed standalone

Operational-Level:
  1. No real-time integration
     • This is a batch-processing prototype
     • Production requires streaming input (Kafka, netflow, etc.)

  2. Model drift
     • Attack patterns evolve; model trained on 2015 data may not generalize
     • Would need regular retraining on current traffic

  3. No interpretable explanations
     • "Why did this flow get flagged?" is hard to answer from tree importances
     • Would need SHAP or LIME for per-prediction explanations

  4. Privacy concerns
     • Storing flow statistics (even anonymized) raises privacy questions
     • Real system needs data minimization & retention policies
